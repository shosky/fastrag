# 对话审计（conversation-trace）— 需求规格

> 2026-10-14 由 idd-spec 依据 grill 裁决记录（`fastrag/.tmp/idd-conversation-trace-grill-decisions.md`，四批 D1-D17 全部代裁已决）编写。
> 事实基线：引擎内已有工具调用就地收集（agent REQ-E08），SSE 事件易失 60s 清理不可回放（agent REQ-D01/D02）——本特性补「事后无法回看」的持久化空缺。

## 范围 {#scope}

对话审计为对话执行提供**内容级、步骤级**的事后留痕与审计回看：每轮对话中引擎的每次 LLM 调用（请求消息、返回内容、思考内容、工具调用请求、用量、耗时）与每次工具调用（工具名、参数、原始输出、成败、耗时）逐行落专门审计表；每轮 run 以追踪标识（Trace ID）串起全部步骤并回填到当轮助手消息，使「会话 → 多轮 → 每轮思考步骤」可查询。查询侧为管理端三级视图（审计会话列表 → 会话多轮明细 → 步骤时间线），归运营模块只读消费。记录范围覆盖全部对话执行入口：会话中心新通道、旧应用通道（二者共享执行核）与独立智能体运行。留存 180 天并交付周期清理。本特性是纯增量的可观测性特性，不改变任何既有对话行为。

## 排除范围 {#out-of-scope}

- **query_kb 检索断链修复**：对话内知识库工具走的 `KbOperationServiceImpl.queryKnowledgeBase` 是未接 RetrievalService 的占位桩（返回伪造文本）——本特性对该工具的审计是**如实记录桩调用与桩返回**；断链修复归 app-center/retrieval 域既有债务。〔裁决 D3 背景〕
- **model_call_log 激活**：该半死表（读端模型监控活跃、写端零实现）的统计语义归模型监控域，本特性不激活、不扩列；全系统 LLM 调用统计另行立项。〔裁决 D5〕
- **会话链外 LLM 调用的留痕**：起标题、查询改写、QA 提炼、图谱抽取、文档解析、评测、连通性测试等辅助调用不入审计表，其日志维持 SLF4J 现状。〔裁决 D4〕
- **会话属主自看步骤级明细**：v1 审计查询仅管理端；属主继续使用既有消息级历史回看（new-conversation REQ-F02）。步骤级自看待真实需求立项。
- **脱敏与字段掩码**：对齐 2026-09-24 决议「暂不脱敏、原文留存」。〔裁决 D15〕
- **审计事件实时推送**：不提供审计流的 SSE 推送或实时大屏，仅事后查询。
- **并入统一日志（UnifiedLog）**：操作级审计与内容级审计粒度、消费场景不同，不合并查询面。〔裁决 D13〕
- **SLF4J 打印面改动**：不新增控制台实时打印开关——落表加查看模块已覆盖「详细查看」诉求。〔裁决 D17〕
- **跨实例审计聚合**：单 run 的收集与落表在同一进程内完成，不做跨实例汇聚。

## 功能需求 {#requirements}

### 4.1 采集范围与埋点

采集点在执行引擎的工具循环层——这是唯一能同时看到「每次 LLM 调用」与「每次工具执行」细节、又能拿到运行上下文的位置。三条执行路径（会话中心新通道、旧应用通道、独立智能体运行）全部经过引擎，一次埋点全覆盖。采集不区分工具类型：内置工具、API 工具、MCP 工具、知识库工具、数据库工具、沙箱工具、子代理调用统一按「一次工具执行一行」记录。

- **REQ-CT-A01**：当对话执行经引擎运行时（会话双入口与独立智能体运行任一路径），系统应为该次运行生成全局唯一的追踪标识，并为运行期间每次 LLM 调用与每次工具执行各记录一行对话步骤。〔裁决 D2/D3/D7〕
- **REQ-CT-A02**：当一次 LLM 调用发生在对话运行内时，系统应记录该次调用的请求消息、返回内容、思考内容、工具调用请求列表、模型标识、token 用量、结束原因与耗时。〔裁决 D3/D6〕
- **REQ-CT-A03**：当一次工具执行发生在对话运行内时，系统应记录工具名、调用参数、工具原始输出、成功与否、错误信息与耗时；原始输出为回传给模型语义的**截断前**值（截断护栏见 REQ-CT-B05）。〔裁决 D3/D8〕
- **REQ-CT-A04**：编排器发起对话执行时，系统应把会话标识传入执行上下文，使该次运行产生的全部步骤可关联回所属会话；独立智能体运行无会话时该标识为空且采集不中断。〔裁决 D3 衍生改动〕
- **REQ-CT-A05**：系统应为每行步骤维护运行内序号；同一运行的全部步骤按序号排列可完整重放该轮的思考与行动序列。〔裁决 D7〕

### 4.2 落表与内容口径

物理载体是引擎域的一张专用步骤日志表（表结构与字段命名归契约层），一步骤一行。内容口径是本特性的核心价值：审计回答「模型与工具到底收发了什么」，而非仅「发生了什么」——因此 LLM 请求内容全量可还原、工具输出存原始值，同时以截断护栏约束存储放大。

- **REQ-CT-B01**：系统应将对话步骤逐行持久化到专用审计表，每行包含：追踪标识、运行标识、会话标识（可空）、运行内序号、步骤类型（LLM 调用/工具调用）、4.1 所列内容字段、截断标记与创建时间。〔裁决 D5/D6〕
- **REQ-CT-B02**：当一轮对话的助手消息落库时，系统应把该轮追踪标识回填到该消息记录，使会话视角的「轮 → 步骤」查询无需额外映射。〔裁决 D7〕
- **REQ-CT-B03**：LLM 请求内容采用增量存储：每轮首个 LLM 步骤记录完整请求基线（系统提示 + 历史投影 + 用户输入），后续 LLM 步骤仅记录相对上一步骤新增的消息；每个 LLM 步骤附请求元数据（消息条数与总字符量）。〔裁决 D8〕
- **REQ-CT-B04**：给定一轮运行的步骤序列，系统应能在查询侧按运行内序号重放增量、组装出每次 LLM 调用的完整真实请求（含中间件改写后的实际内容），组装由服务端完成、增量存储协议不对查询方暴露。〔裁决 D8；澄清项 3〕
- **REQ-CT-B05**：系统应对内容施加截断护栏：单工具输出上限 32KB、单 LLM 步骤请求增量上限 64KB，超限部分截断存储并置截断标记。〔裁决 D8〕
- **REQ-CT-B06**：步骤内容以引擎视角真实收发为准：LLM 请求中的输入消息为敏感词输入过滤**后**的内容，模型返回为输出过滤**前**的原始内容。〔裁决 D16〕

### 4.3 写入时机与失败容忍

步骤在运行期间于内存收集，运行终态一次性批量落表——与助手消息落库同一时点。落表是审计职责而非对话职责：任何落表失败不得影响对话结果、响应或延迟特征。

- **REQ-CT-C01**：当运行进入终态（完成/停止/超时/错误）时，系统应将该运行内存收集的全部步骤一次性批量落表，与当轮助手消息落库同点完成。〔裁决 D9〕
- **REQ-CT-C02**：如果步骤落表失败，系统应仅记录告警日志并放弃该批步骤，对话结果、前端响应与流关闭行为不受任何影响。〔裁决 D9；对齐 agent NFR02〕
- **REQ-CT-C03**：当进程在运行终态前终止时，该运行的步骤不落表且无残留副作用（已登记代价：崩溃丢当轮审计，与 SSE 事件易失同级）。〔裁决 D9〕

### 4.4 审计查询

查询端归运营模块只读消费（其「日志产生端归各业务域」的边界不被打破），三级视图自上而下：审计会话列表定位目标 → 会话多轮明细看对话全貌 → 步骤时间线看单轮思考步骤。独立智能体运行无会话承载，在列表中以运行自身信息呈现。

- **REQ-CT-D01**：管理端可分页查询审计会话列表，支持按时间范围、用户、关键词、模型与来源（直聊/挂应用/独立运行）筛选，返回统一分页结构。〔裁决 D12〕
- **REQ-CT-D02**：管理端可查看单个会话的多轮消息明细及每轮消息关联的追踪标识。〔裁决 D12〕
- **REQ-CT-D03**：管理端可按追踪标识查询步骤时间线：步骤按运行内序号升序交错展示（LLM 调用与工具调用），每步可查看完整内容。〔裁决 D12〕
- **REQ-CT-D04**：当追踪记录无关联合会话（独立智能体运行）时，系统应在列表中以运行输入摘要作为来源标识呈现，查询不报错。〔裁决 D2；澄清项 2〕
- **REQ-CT-D05**：审计查询端点应要求管理端权限，并按组织数据范围过滤（对齐模型监控的组织过滤先例）；权限键与菜单种子归契约层。〔裁决 D11；澄清项 5〕

### 4.5 留存与清理

内容级日志的体积远超操作级日志，留存必须配清理，二者同批交付。留存期对齐既有三日志决议（180 天）。

- **REQ-CT-E01**：系统应保留对话步骤日志缺省 180 天，留存天数可配置。〔裁决 D14；澄清项 4〕
- **REQ-CT-E02**：系统应周期性（每日）批量删除超期步骤日志，单批删除量受上限约束；清理执行期间在线对话的写入与查询不中断。〔裁决 D14〕

## 约束 {#constraints}

- **落表非关键路径**：步骤收集与落表不得增加对话关键路径的同步写库次数（运行期零落库写、终态一次批量）；落表失败仅告警（REQ-CT-C02）。〔裁决 D9〕
- **崩溃窗口代价（已接受）**：进程终止丢当轮审计，不为此引入运行中期写库。〔裁决 D9〕
- **存储护栏**：单步内容受 REQ-CT-B05 上限约束；内容列类型与索引设计归契约层，须支撑按（追踪标识+序号）、（会话+时间）、（时间，清理用）三类查询。〔裁决 D6/D8〕
- **DDL 双处同步**：本特性新增持久化结构（步骤日志表、助手消息追踪标识列）的 DDL 必须在 SchemaInitializer 幂等增补与 init-scripts/schema.sql 全量脚本双处同步，并列入验收（历史漂移教训：idx_content_fulltext 单侧、agent 表缺失）。〔裁决 D6〕
- **凭据红线继承**：技能 env 凭据值由既有凭据通道保证不进 prompt/事件/日志，审计表自然不含；审计侧不做额外脱敏处理。〔裁决 D15；CONTEXT.md「技能凭据通道」〕
- **查询权限**：审计查询为管理端能力，鉴权与数据范围过滤见 REQ-CT-D05。〔裁决 D11〕

## 验收清单 {#acceptance}

- [ ] 会话中心新通道、旧应用通道、独立智能体运行三种路径各执行一轮含工具调用的对话，均产生追踪记录与步骤行（REQ-CT-A01）
- [ ] 一次 LLM 调用产生一行 LLM 步骤，含请求/返回/思考/工具调用请求/模型/用量/结束原因/耗时（REQ-CT-A02）
- [ ] 一次工具执行产生一行工具步骤，输出为截断前原始值；MCP、数据库、沙箱工具各验证一种（REQ-CT-A03）
- [ ] 独立智能体运行的步骤可查且会话标识为空，不中断采集（REQ-CT-A04）
- [ ] 同一运行步骤按序号排列可重放完整思考与行动序列（REQ-CT-A05）
- [ ] 步骤行落专用审计表且关联字段（追踪标识/运行标识/会话标识/序号/类型/内容/截断标记/时间）齐全（REQ-CT-B01）
- [ ] 助手消息记录携带当轮追踪标识（REQ-CT-B02）
- [ ] 多迭代对话中：首步为完整基线、后续步骤为增量、每步带消息数与字符量元数据（REQ-CT-B03）
- [ ] 查询接口返回的每步完整请求与引擎实际发送一致（含中间件改写），增量协议不外露（REQ-CT-B04）
- [ ] 超 32KB 工具输出被截断且有标记；超 64KB 请求增量同口径（REQ-CT-B05）
- [ ] 输入敏感词命中被替换为过滤后内容进入审计；模型输出含被过滤原文（REQ-CT-B06）
- [ ] 运行终态一次批量落表；运行期间对该表无写操作（REQ-CT-C01）
- [ ] 人为注入落表失败：对话正常完成、前端无感知、告警日志出现（REQ-CT-C02）
- [ ] 运行进行中强行终止进程：重启后该轮无步骤行落库、无半批残留（REQ-CT-C03）
- [ ] 审计列表筛选（时间/用户/关键词/模型/来源）与分页结构正确（REQ-CT-D01）
- [ ] 会话明细展示多轮消息与各轮追踪标识（REQ-CT-D02）
- [ ] 步骤时间线按序号升序交错展示 LLM 调用与工具调用，每步内容可展开（REQ-CT-D03）
- [ ] 独立运行在列表以输入摘要呈现、详情可开且不报错（REQ-CT-D04）
- [ ] 无管理权限访问审计端点被拒绝；组织外数据不可见（REQ-CT-D05）
- [ ] 留存天数缺省 180 且可配置（REQ-CT-E01）
- [ ] 清理任务删除超期行且单批有上限，清理期间写入与查询不中断（REQ-CT-E02）
- [ ] 步骤日志表与消息追踪标识列在 SchemaInitializer 与 schema.sql 双处存在且一致（约束）

## 测试策略 {#testing}

经由公共接口与引擎测试缝测试。LlmService 与工具执行器全部 mock（沿用 AgentEngine 既有测试模式），MySQL 写入走真库（MyBatis-Plus）。重点用例族：

①采集覆盖——三入口各跑一轮含多工具对话，断言步骤行数、顺序与字段完整性（4.1）。②增量重放一致性——多迭代场景下按基线+增量重放的结果与引擎实际请求逐字段相等（4.2，本特性最重要的正确性断言）。③护栏边界——32KB/64KB 阈值两侧取样断言截断标记（4.2，纯函数用例族）。④失败容忍——注入落表异常断言对话无感（4.3）。⑤查询三级视图——列表筛选、会话明细、时间线组装（4.4）。⑥独立运行分支——无会话标识的采集与呈现（4.1/4.4）。⑦清理任务——超期批删与在线写入并存（4.5）。⑧DDL 双处一致性守护测试（对齐 SkillDdlParityTest 先例）。
