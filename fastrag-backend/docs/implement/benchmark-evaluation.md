## 2. Interface Implementations

### BenchmarkGenerator（from contract: benchmark-evaluation.BenchmarkGenerator）

**Logic Flow:**（BenchmarkServiceImpl.generate 同步段 :117-143 → BenchmarkGenerationHelper.generateQuestions :79-139）

1. 同步段：new KbBenchmark → 填 kbId/name/description、isAutoGenerated=1、questionCount=config 缺省 10、hasGoldChunks=hasGoldAnswer=1、buildMethod 缺省 "vector" → insert → try 写操作日志（失败 warn）→ 调 generationHelper.generateQuestions（独立 Bean 保 @Async 代理）→ RETURN 记录（不等生成）。
2. 异步段：解析模型名（llmModel 空白→"default"）。
3. IF buildMethod=="graph" THEN buildGraphPrompt ELSE buildVectorPrompt。
   - buildVectorPrompt（:215-259）：candidateCount 缺省 5 → `SELECT id,content FROM kb_chunk WHERE kb_id=? ORDER BY id LIMIT min(c*3,30)`；IF 空 THEN 返回一般知识出题模板 ELSE 取前 candidateCount 条拼上下文（每条截 500 字符）；crossBoundary=true 时切换为「答案横跨两个相邻片段、goldChunks 必含两个相邻 id」要求模板。
   - buildGraphPrompt（:261-344）：实体 20 条 + 关系 20 条拼列表 → 按前 5 个实体名 LIKE 查 kb_chunk 10 条作 goldChunks 候选 → 有候选则要求填完整 id，无候选 goldChunks 约定 []。
4. callLlm（:187-213）：model=="default" → chatWithTimeout(model, prompt, null, null, false, benchmarkLlmTimeoutSeconds(缺省 300), 8192)；ELSE 查 model 表（code= ? LIMIT 1）取 api_url/api_key_ref → 成功带地址调用；查无/异常 → warn 降级默认网关再调。
5. parseResponse（:145-162）：空/空白→空列表；BenchmarkResponseParser.parseQuestions（剥围栏→截 [..]→JSONUtil.toList；损坏 JSON 上抛）catch 后记响应预览（300 字符）返回空列表。
6. IF 题目空 THEN resetQuestionCount（题数≠0 则清零，事务内）RETURN。
7. ELSE 逐题建实体（questionIndex=i 连续、crossBoundary→1/0、goldChunks List→JSON 串或 String 直用）→ 事务{逐条 insert + 重查基准覆盖 questionCount=实际数} → info 记账。
8. 任意异常：error 日志 → resetQuestionCount 清零（自身再 try-catch）。
9. 状态转移：kb_benchmark 仅 question_count 变化（请求值→实际值/0）；无状态字段。

**Module Interactions:**
- Calls：LlmService.chatWithTimeout（流式收集长超时）、JdbcTemplate（kb_chunk/kb_graph_entity/kb_graph_relation/model 四类只读 SQL）、TransactionTemplate、KbBenchmarkMapper/KbBenchmarkQuestionMapper、LogService（publish 模块）。
- Called by：仅 BenchmarkServiceImpl.generate（@Async 代理入口）。
- Shared state：kb_benchmark（question_count 两段式协议）、kb_benchmark_question（插入方）；无缓存/队列/主题。
- 外部模块交互：无 MQ、无 Redis。

**Decisions & Deviations:**（与契约的偏离+理由）
- 无行为偏离；关键取舍：① 出题语料 vector 路按 `ORDER BY id` 取前 N 而非随机采样——实现简单但多次生成语料重叠（登记债务）；② 失败「清零」而非「置失败标志」——表无生成状态字段，题数即唯一信号（契约 Post 如实登记）；③ 跨界约束仅存在于 prompt，无落库校验（LLM 不遵从时 goldChunks 可能非两个 id，契约已深证 CERTAIN——2026-09-24；JSONL 导入路径同样无校验与长度防御，512 列上限风险见 data.md gold_chunks 决议）；④ model 表路由 SQL 不带 status=online 过滤（与 retrieval/graph 上游口径不一致，data.md 消费点登记）。
- importFromJsonl（:158-227）实现完整但全后端零调用方：逐行 readTree、question 空白跳过、坏行 warn、事务{批量 insert + 题数累加 + has_gold_answer=1}、操作日志 benchmark_imported——死代码冻结，属门面实现（无契约接口）。

**Parent Trace:** [generateQuestions] → [BenchmarkGenerator] → [Design.BenchmarkGenerator（缝 1）] → [REQ-B01~B06]；[generate 同步段] → [BenchmarkGenerator.Pre] → [Design.BenchmarkFacade] → [REQ-B01]。

### EvaluationExecutor（from contract: benchmark-evaluation.EvaluationExecutor）

**Logic Flow:**（EvaluationServiceImpl.run :86-130 → EvaluationExecutionHelper.execute :111-247）

1. run：IF config.benchmark 空白 THEN createFailedEvaluation（status=failed、三计数 0、insert）RETURN 该记录。ELSE count 基准题目；IF 0 THEN 同上拒绝。ELSE new KbEvaluation（status="running"、completedCount=0）→ insert → try 操作日志（evaluation_run）→ executionHelper.execute（独立 Bean 保 @Async）→ RETURN running 记录。
2. execute：解析缺省（retrievalMode 缺省 "hybrid"、enableRerank=TRUE.equals）→ info 开跑记账。
3. 加载题目列表；IF 评测记录不存在 THEN warn RETURN（无终态可写）。ELSE dataCount=题目数 → update。
4. IF 题目空 THEN 事务{status=failed、completedCount=0、dataCount=0} RETURN（E_BENCHMARK_EMPTY 竞态路径）。
5. 批量 Embedding（:384-409）：resolveModelApi(embeddingModel) 非空 → embed(model, queries, apiUrl, apiKey) 一次调用；ELSE 逐条 embed；异常 → 逐条以 "default" 重试，仍失败以空向量占位。
6. 并行逐题（Semaphore(4) + 4 守护线程 "eval-worker"，CompletableFuture.supplyAsync）；逐 future.join 收集 QuestionResult（join 异常仅 warn 计 0——该题无结果行、指标算 0）。
7. 单题 evaluateQuestion（:258-377）：
   - 检索：retrieveChunksWithVector(kbId, query, topK=10, 预计算向量, mode, ...) → switch{vector: 空向量→fulltext；milvus search(collection="kb_"+kbId, topK*3)→回表按 scoreMap 排序，空/异常→fulltext；hybrid: 向量 2×topK + fulltext 2×topK → RRF(k=60) 融合取 topK，异常→fulltext；fulltext/default: 关键词 `+词*` MATCH...AGAINST → 异常→LIKE OR}；rerank 开启 → rerankResults（modelApi 有无两态；空结果/异常→原序截 topK）。
   - R@K：parseGoldChunks（JSON 解析失败→空）→ checkRecall（gold 空→false；前 K 条含任一 gold→true），K=1/3/5/10。
   - 合并评判：llmModel = judgeModel 非空且 ≠ answerModel ? judgeModel : answerModel；topChunks = 前 2 条；buildContext（每条截 300 字）；generateAnswerWithJudgment：context 空→直接返回判错 JSON；prompt（内容/问题/标准答案/严格 JSON {"a","c"}）→ resolveModelApi 路由 chat → parseJudgmentResponse（「模型调用失败」前缀→规则评判；剥 ```；解析 isCorrect|c、answer|a；解析失败→规则评判）；外层再 catch 一次解析（:294-314）→ ruleBasedJudge（空答案判错；数字命中率≥0.8；2~4 字中文关键词命中率≥0.8；无可校验内容判错）。
   - 跨界题（crossBoundary==1）：completeRaw = judgeContextCompleteness(topChunks 上下文各截 600)；completeExt = 同法于 extendWithParents（按 parent_id 查父块全文）+各截 1200；judgeContextCompleteness：空短路 NULL、context>8000 截断、prompt 要点支撑 {"supported","total"}→比例钳 0~1、失败→ruleBasedCompleteness（2~4 字中文关键词命中比例，无关键词→NULL）；自身异常仅 warn。
   - 检索指标串："R@1 %d.000 ..." + 跨界题附加 "COMPLETE raw -> ext"。
   - 异常：兜底 QuestionResult（全零 R@K、"评估失败: msg"、"执行异常"、isCorrect=0）。
8. 聚合（:216-235）：duration=起止差；各率=命中数/total（total 恒=题目数，join 异常题计 0）；overallScore=R@10×0.7+accuracy×0.3。
9. 结果落库：逐条 insert（非事务）。
10. finishEvaluation（:889-912，事务）：status=completed、completedCount=dataCount=benchmarkCount=total、duration、四 R@K、accuracy、overallScore → update。info 完成记账。
11. 全程 catch（:237-246）：error 日志 → 事务{status=failed}。
12. 状态转移：running →（completed | failed）；失败子路径：空题→failed、异常→failed；单题失败不转整体状态。
13. 错误恢复：D_QUESTION_FAILED 兜底行、D_JUDGE_RULE_FALLBACK 规则评判、D_RETRIEVAL_DEGRADED 全文降级、E_EXECUTION_FAILED failed 终态（均已在契约登记）。

**Module Interactions:**
- Calls：EmbeddingService.embed（批量/单条两态）、MilvusService.search、RerankService.rerank（带/不带 modelApi 两态）、LlmService.chat（合并评判与完整度两场景）、JdbcTemplate（kb_chunk 检索/回表/父块、model 表路由）、TransactionTemplate、KbEvaluationMapper/KbEvaluationResultMapper/KbBenchmarkQuestionMapper；间接被 run 操作日志触达 LogService。
- Called by：仅 EvaluationServiceImpl.run（@Async 代理入口）。
- Shared state：kb_evaluation（状态机行，run 建执行改）、kb_evaluation_result（唯一写方）；无缓存/队列/主题。
- 外部模块交互：无 MQ、无 Redis；Milvus collection 命名 "kb_"+kbId 拼接（与 chunk-management 约定一致性未在本链验证）。

**Decisions & Deviations:**
- **与上游契约的实质偏离（ADR-1 已声明）**：不消费 RetrievalSearchEngine，自带三模式精简管线——理由：跨次跑分可比性（配置面窄）、批量预计算向量复用。后果：无 chunkType='parent' 过滤（父分片可能进入检索结果参与 R@K 判定，与 retrieval 引擎口径不同）、无 graph/qa/clause 通道。
- 结果落库逐条 insert 非事务（:230-232）——中途异常将留下 failed + 部分结果行（契约债务 ①）。
- completedCount 无逐题递增——并行聚合后一次写终值，进度查询呈 0→终值跳变（data.md 已深证 CERTAIN，2026-09-24）。
- 合并评判把 answerModel/judgeModel 压缩为单次调用模型（judge 优先）：answerModel 在「judge 缺省或相同」时才实际生效——配置语义与字面直觉有差（契约 Input 已注明）。
- 评判 LLM 只喂 top-2 chunk、每条截 300 字：token 优化直接压低 R@K 之外的答案质量上限（契约债务 ④）。
- join 异常题（:211-213）既无结果行也计 0 分——与 D_QUESTION_FAILED 兜底行路径（evaluateQuestion 内部 catch）不同，是第二层失败隔离，契约 Error modes 未单列‹CERTAIN（2026-09-24 深证：evaluateQuestion :267 起 try 覆盖除 query getter 外全部主体、:362-376 全 catch 兜底返回，Exception 面上恒正常返回；join 抛出仅剩 Error/catch 自身缺陷/聚合日志行 NPE 等「自身 bug」形态）›。
- 控制器死字段：两 Controller 注入的 logService 从未使用（日志全在 service 层）——初始化债，无行为影响。
- BenchmarkServiceImpl.getDetail/listQuestions/delete 不校验 kbId（selectById/deleteById 直查）——与 EvaluationFacade 的 kbId+id 双键口径不一致（design 债务 ②）。

**Parent Trace:** [execute + run 拒绝协议] → [EvaluationExecutor] → [Design.EvaluationExecutor（缝 2/缝 3 + EvalRetrievalPipeline）] → [REQ-C01~C06、REQ-D01~D07]；[getDetail/status/delete] → [EvaluationExecutor Output 读面] → [Design.EvaluationFacade] → [REQ-C05、C07、D07]。
