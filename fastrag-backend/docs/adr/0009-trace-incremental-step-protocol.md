# LLM 请求内容按基线加增量存储并由服务端重放

**Date:** 2026-10-15
**Status:** Accepted（grill 裁决 D8，2026-10-14）

## 背景 {#context}

引擎单轮最多 15 次迭代，每次 LLM 调用都携带全量历史消息（系统提示 + 历史投影 + 此前迭代的工具结果），且中间件（摘要/技能/历史注入）会改写实际发送内容。审计要求「可还原每次真实发送的完整请求」，但全量快照意味着单轮存储随迭代数平方增长。

## 决策 {#decision}

每轮首个 LLM 步骤存完整请求基线，后续 LLM 步骤仅存相对上一步新增的消息（附消息条数/字符元数据）；查询侧由 TraceTimelineAssembler（IF-002）在服务端按 step_seq 重放组装出每步完整请求，增量存储协议不对查询方暴露。

## 已考虑的替代方案 {#alternatives}

**每步全量快照** — 拒绝：15 迭代 × 全量历史的 O(n²) 存储放大，长会话下单轮可达数十 MB，留存 180 天的体积不可接受。

**只存摘要或截断内容** — 拒绝：审计的核心价值是回答「模型与工具到底收发了什么」，摘要化直接摧毁 REQ-CT-B04 的重放口径。

**前端按增量拼装** — 拒绝：增量协议泄漏到查询方，协议任何演进都被前端版本锁死；且多消费方（运营页/未来属主自看）各自实现拼装必然漂移。

## 后果 {#consequences}

存储从 O(n²) 降为 O(n) 且单步受 64KB 护栏约束；代价是「重放正确性」成为本特性最重的测试断言（spec 测试策略②：重放结果与引擎实际发送逐字段相等），且增量链依赖基线行存活——基线被留存清理先删时降级为 gap 标记（ERR-TRACE-GAP）而非报错。协议演进被收敛在 trace 包编解码对内，前端与运营模块零感知。
