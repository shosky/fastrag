## 背景 {#context}

Widget 模板需要表达卡片布局与数据填充（spec REQ-WG-A01/D03）。对标 ADP 的组件属性体系之外，模板语言还有一个隐藏维度：**表达力等级**。引入条件/循环/表达式语法（v-if、循环列表推导、算式）意味着渲染端要内嵌表达式求值器——校验面（保存时无法静态判定分支正确性）、安全面（表达式注入与 XSS 面，禁 v-html 的消毒基线被绕开）、生成面（LLM 产出合法表达式的错误率显著高于产出合法 JSON）三者复杂度同时陡增。

而一期四场景（澄清询问/过程反馈/信息确认/结果展示）的分支差异，实际由对话中的智能体承担：LLM 本来就在逐轮决策——需要不同形态时换一个模板或换一份数据即可，模板内的静态分支是冗余机制。快照 #16 已裁决「无表达式/条件语法」。

## 决策 {#decision}

模板 DSL 固化为：**JSON 组件树 `{type, props, children[]}`**；字符串 prop 支持 `{{varName}}` 占位插值；渲染数据 = default 先填充、data 覆盖合并。**不做**表达式求值、条件渲染、循环渲染；组件列表渲染由 ListView/ListViewItem 承担（children 结构化表达，非语法层循环）。安全底线配套：三档保存校验（REQ-WG-A02）+ 组件白名单双端一致（REQ-WG-A06）+ 渲染端禁 v-html 与图片协议白名单（widget-frontend 契约不变量）。

## 后果 {#consequences}

- **得到**：保存校验静态可判定（三档校验是纯结构检查）；渲染器实现为纯递归 + 插值，无求值器攻击面；LLM 生成模板的可靠性高（合法 JSON 即合法模板的下界）。
- **代价**：模板表达力受限——同一资产无法在数据不同时呈现结构性差异，需拆多模板或用数据驱动的显示开关（如空字符串插值隐藏文本）；复杂布局靠 Row/Col 嵌套手写，创作成本高于可视化方案（一期手写 JSON 的已知定位）。
- **不可逆提示**：已授权的模板依赖此 DSL 形态；未来若引入模板语言属破坏性变更（存量模板迁移），非目标登记在 spec 排除范围——需要时另立特性链重开评估。
