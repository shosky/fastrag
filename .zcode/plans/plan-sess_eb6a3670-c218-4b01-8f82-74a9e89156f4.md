## 修复知识图谱文件级开关的 3 处歧义

### 问题回顾
1. **打开开关 = 全量重处理**（`processFile` 重解析→分块→向量化→图谱），太重了
2. **关闭开关不清理已有图谱数据**，语义不一致
3. **开关状态 ≠ 图谱实际状态**，用户无法得知构建进度

---

### 改动 1：打开开关 → 仅构建图谱（不再全量重处理）

**前端 `api/index.ts`：**
- 扩展 `buildGraphIndex(kbId)` 为 `buildGraphIndex(kbId, fileIds?, mode?)`，支持传 `fileIds` 数组和 `mode` 参数
- 新增 `deleteFileGraph(kbId, fileId)` 函数，调用 `DELETE /kb/{kbId}/graph/file/{fileId}`

**前端 `FileManager.vue`：**
- `handleToggleGraphBuild` 中，打开时不再调用 `api.processFile`，改为调用 `buildGraphIndex(kbId, [fileId], 'full')` 仅触发图谱构建
- 关闭时调用 `deleteFileGraph(kbId, fileId)` 清理图谱数据

**前端 `FileTable.vue`：**
- 开关打开时设 loading 状态，通过已有轮询机制（`startPolling`）监听文件处理状态

---

### 改动 2：关闭开关 → 清理图谱数据

**后端 `GraphServiceImpl.java`：**
- `deleteFileGraph` 方法中，在 `graphStore.deleteFileGraph(kbId, fileId)` 之后，用已有的 `jdbcTemplate` 重置该文件 chunks 的 `graph_indexed = 0`：
  ```java
  jdbcTemplate.update(
      "UPDATE kb_chunk SET graph_indexed = 0 WHERE kb_id = ? AND file_id = ?", kbId, fileId);
  ```
- 放在 `refreshIndexAfterDelete` 之前，让缓存刷新能正确反映重置后的计数

---

### 改动汇总

| 文件 | 变更 |
|------|------|
| `fastrag-frontend/src/api/index.ts` | 扩展 `buildGraphIndex` 签名支持 fileIds/mode；新增 `deleteFileGraph` |
| `fastrag-frontend/src/views/.../FileManager.vue` | 打开→调用图谱构建API；关闭→调用删除图谱API |
| `fastrag-backend/.../GraphServiceImpl.java` | `deleteFileGraph` 中增加 `graph_indexed=0` 重置 |

**不改动：** `FileTable.vue` 开关 UI、`useFiles.ts`（已修复导出）、后端 `FileController`/`FileServiceImpl` 的 update 逻辑、`IngestionConsumer`/`GraphBuildConsumer`。
